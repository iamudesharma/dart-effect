## Upgrade behavior

Pending work has explicit limits. SQL pending leases default to 1024, HTTP
requests/SSE sessions to 32, OpenAI requests/streams to 64, and cache owners to
twice resident capacity. Core waiting queues also have configurable bounds.
Handle overload errors and review exhaustive enum switches when upgrading.
Limits count owned work, not arbitrary payload bytes retained by callers.

HTTP response bodies use immutable packed bytes; aggregate active accumulation
has a separate 32 MiB default budget. SQL preserves both execution and prepared
cleanup failure and discards uncertain sessions. Core uses elapsed clocks for
durations, preserves deep cleanup causes and avoids unnecessary allocations.
Scheduling fairness and cooperative cancellation are preserved.

Cache supports single-flight LRU values, independent waiter cancellation,
nullable values, explicit maintenance, scoped borrower lifetimes and awaited
cleanup. Include authorization identity in keys. TTL is lazy: use purge or
maintenance when idle expiry must release values. Close caches before shutting
down their borrowed runtime; inspect returned cleanup diagnostics.

## Executed release checks

- Clean analyzer and formatting; five type fixtures; executable examples and web compilation.
- 269 VM and 245 Chrome tests across the seven implemented packages.
- Cache: 38 VM and 37 Chrome tests, real loopback HTTP fixture, deterministic LRU
  scenarios, JIT/AOT checks and three fresh VM retention processes. All 117
  tracked cache owners/payloads were collected after awaited cleanup and GC.
- Actual PostgreSQL/MySQL acceptance and examples. The general DB runner skips
  six TLS-specific tests; the separate trusted-CA runner executes all six and
  passes without skips. All owned containers were removed.
- Three fresh saturated-work memory probes release all 36 tracked payloads after
  purge, release or shutdown. A 4 MiB HTTP result retains 4,195,024 bytes in the
  constructor-only measurement; transient/request/decoder memory is separate.
- Standalone candidate archives pass dry-run checks. Each actual publication
  additionally resolves hosted siblings, analyzes and dry-runs without overrides.
- Hosted archive SHA-256 and source comparison, followed by a fresh seven-package
  hosted consumer, are recorded separately in publication-2026-10-21.json.

The release report includes source hashes. Earlier audit and benchmark reports
remain immutable historical records. Benchmark timings are local measurements,
not universal performance promises. Live OpenAI provider acceptance, native
Flutter-device/frame checks and production soak are not part of this run.
Protected cleanup can extend a timeout; arbitrary Futures require a real abort
hook. Tests provide evidence for the covered contracts, not proof of zero bugs.

## Reproduce

```sh
python3 tool/sql_integration.py --report build/memory-fixes-sql.json
python3 tool/sql_tls_acceptance.py --report build/release-tls.json
python3 tool/validate_memory_fixes.py --report build/release-validation.json
python3 tool/cache_validation.py --report build/cache-release-validation.json
python3 tool/verify_memory_publication.py
```

`prepare_memory_release.py` creates isolated candidate archives and runs preflight
checks. `publish_memory_release.py` is a publication command, requires explicit
release authorization, and verifies fresh evidence before uploading. Do not use
publication as a test. Never bypass validation or include development overrides,
credentials, upstream snapshots or Node source in archives.
